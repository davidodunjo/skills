# Components and styling

Build from the repo's design system first: its primitives, vendored or generated into the project, are the vocabulary of the UI, and a plain element is used only when the design system has nothing for the job, such as a layout wrapper. Add a missing primitive through the design system's own tooling rather than hand-rolling a look-alike, and adapt its defaults to the repo's conventions once, in the primitive, not at every call site.

Prefer composition to configuration: a component exposes its parts (`Card`, `CardHeader`, `CardContent`) and accepts `children` and slots, rather than growing a boolean or string prop for every variation. Variants that are part of the design, size, intent, emphasis, are declared once with a variant helper and typed from it; one-off adjustments come through `className`. Polymorphism goes through the primitives' render or as-child prop, keeping the inner element's semantics: when a button-styled primitive renders a link, tell the primitive it is no longer a native button so it drops button-only behaviour, or it will warn and break keyboard semantics.

Components expose a small, typed interface: required props for what they cannot work without, optional ones with defaults destructured in the signature, callbacks named `onX` for events and `handleX` inside, and native element props spread through when the component wraps one element, so `aria-*`, `data-*` and event handlers keep working. Keep presentational components free of data fetching; they take data in props and report intent through callbacks, which makes them reusable and trivial to test.

Styling is utility classes against design tokens. Colours, radii, spacing, shadows and typography come from the theme's CSS variables through the utility layer, never raw hex values or arbitrary pixel values in components, so dark mode and re-theming are a token change. The class-merge helper joins variant output, state classes and the incoming `className`; static class lists are plain strings. State styling reads attributes the primitives already set (`data-state`, `data-disabled`, `aria-expanded`) rather than mirroring them in JavaScript. Responsive layout uses container queries where a component's space, not the viewport, decides its layout. No CSS-in-JS runtime, no inline `style` except for values only known at runtime such as a computed position or a user-chosen colour.

Icons come from one icon set, sized by the text they sit beside, decorative ones hidden from assistive technology and meaningful ones labelled. Images declare their dimensions or aspect ratio so layout does not shift, and avatars and covers fall back to initials or a neutral fill when the source is missing.

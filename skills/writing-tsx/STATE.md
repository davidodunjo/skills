# State

Every piece of state has exactly one home, chosen by who owns it and how long it lives, and most bugs in React apps come from state kept in two homes at once. Server data lives in the server-state cache. State a user would share or expect back after a reload lives in the URL. Form values live in the form library until submit. Transient UI state, whether a menu is open or which row is hovered, lives in the component that renders it. Only state that several unrelated components read and that belongs to none of those homes goes into a client store.

Never store what can be computed. Filtered lists, counts, totals, validity and labels are derived during render from the state they come from; a `useEffect` that copies one state into another, or syncs props into state, is a bug waiting for an edge case. When a value must reset as an input changes, key the component on that input instead of resetting it in an effect. Effects are for synchronising with things outside React, subscriptions, timers, the DOM, analytics, and each one cleans up after itself.

Client stores stay small and focused, one per concern rather than one global store, and components subscribe through selectors that return the smallest value they need, with shallow comparison when they select several fields, so an update re-renders only the components that read the change. Store actions live beside the state they change, named as events in the domain (`openPanel`, `dismissNotice`), never as raw setters exported for components to compose. Persisted client state (preferences, dismissed hints, drafts) goes through the store's persistence layer with a version and a migration, never through scattered storage calls.

Context carries dependencies and values that rarely change, the current user, theme, a feature's injected services, not state that updates on every keystroke, since every consumer re-renders when the value changes. Each context is a context, a provider and a hook: the context defaults to `null`, the hook reads it, throws a clear error outside its provider, and returns a non-null value, and the provider assembles one value object.

Tightly coupled state where the next state depends on the event and the current state together, a multi-step wizard, an upload with retries, a drag interaction, is modelled as a reducer or a state machine with a discriminated-union event type and an exhaustive switch that throws on an unknown event, so impossible states cannot be represented. Booleans that can contradict each other (`isLoading` and `isError` both true) are replaced by one status union.

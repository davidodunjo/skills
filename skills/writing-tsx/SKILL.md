name: writing-tsx
description: Use when writing or editing frontend code in TSX & React.
---

Stack-agnostic within React/TSX: describes structure, naming, and shape, not specific libraries. Overlaps with `writing-code`; these rules win within frontend scope. A repo's own structure or convention document wins over this skill wherever the two disagree.

**Components**

Components are named function declarations, never arrow consts. Export style matches what the repo already does, named exports when it has no precedent, one component export per file. Prop types are `type` aliases named after the component (`BoardCardProps`), never bare `Props`, never inlined into the signature. Props come in as a single `props` param, destructured on the first line; no-prop components take empty `()`. Body order is fixed: destructure, data hooks, derived values, handlers, early-return guards, remaining derived values, JSX last. Handlers are `function handleX() {}` declarations except one-off inline callbacks. `useCallback`/`useMemo` stay out of presentational components, only providers, custom hooks, and genuinely expensive components get them. Guards return before the main JSX for special cases and empty or not-found data; loading and error are not guards inside components when the data layer suspends, they belong to the route. Every collection renders one shared empty-state component with a short message and, where it makes sense, the primary action, and a missing record renders a not-found state, never a silent `null`. No comments, no doc blocks. `memo()` wraps the export only for expensive or frequently re-rendered components. Server-component frameworks get the client directive as the first line of top-level view/form/layout/page files, omitted on leaves. No `forwardRef`, components declare `ref?:` directly in their prop type and destructure it; components needing both an internal and forwarded ref hand-roll a merging callback. `useImperativeHandle` exposes a small named-method object, no dependency array, handle type inlined into `ref?:`. `useRef<T>(null)` for DOM nodes, `useRef<T | undefined>(undefined)` for mutable holders.

**Data**

Data a page needs is fetched by its route, not discovered by its components, so loading starts on navigation or link preload instead of after render and requests never waterfall. Each read is one query-options factory that co-locates key and fetcher; the route's loader prefetches it and the component reads it with the suspending hook, so the component renders with data present and never branches on loading, while pending and error UI live once per route in its pending and error components. Keys come from one factory per resource with a hierarchy (`all`, `lists`, `list(filters)`, `detail(id)`), so a write invalidates exactly the slice it changed and a broad refresh is one call. Writes are one hook per operation wrapping the mutation, invalidating through the key factory and awaiting it so the screen never shows stale data; when a write is cheap and likely to succeed, show it optimistically from the mutation's pending variables rather than hand-patching the cache. State a user would share or expect back after a reload (search, filters, sort, page, selected tab) lives in validated URL search params that feed the query keys, and only transient UI state stays in components. Services export one plain object of typed async endpoint methods and are the only code that knows the transport; views and components never import them. A reactive backend such as Convex keeps the same shape, its generated queries standing in for the service and fetcher. Domain types live with the resource's API code as `type` aliases with union literals and optional fields. Models are factory functions that fill defaults for every shape a form creates, nested ones included, so no form builds an empty record from an inline literal. Custom hooks stay single-responsibility, minimal deps, and throw when used outside their required provider.

**Forms**

Forms declare their validation schema at the top of the module, validators carry inline human-readable messages, and the form type is inferred from the schema. Initialize with validate-on-change, the schema resolver, and default values from the record the route already loaded or from a model factory for new records. Destructure form state, then validity/dirty/errors on a separate line. Every input binds through the form library's controller with an error flag and helper message. Submit handler is named `onSubmit`, signature `(formData) => ...`, wired through the library's submit wrapper; submit button disabled while pristine or invalid, showing a pending state while the write runs. Multi-tab forms share state through the form provider, each tab reading from form context. Server-side field errors map back through the library's set-error API. Inline and dialog forms auto-save via debounced changes through an update mutation instead of an explicit submit.

**Files and folders**

A file earns a folder only when it gains private companions: once a component needs sub-components, hooks or types that nothing else uses, it becomes a folder named after it holding the component and those companions, and code belonging to one resource groups under that resource (`api/contacts/`, `api/tags/`) once there are two or more such files. Never create a folder for a single file or ahead of need. When a second consumer appears, move the shared piece up to the nearest folder both consumers already live under, not to a global shared folder.

**Context**

Each React context is a three-file folder: the context (type plus `createContext`), the provider, the hook. `createContext` gets a null/undefined default to force the hook's null-check, and the consuming hook calls `useContext`, null-checks, and throws outside its provider. The provider holds local state and assembles the value object it passes down, using the `<Context value={...}>` form.

**Styling**

Layout, spacing, and typography use utility classes; theme-token and computed styles use the inline style prop; CSS pseudo-state and transitions go through a styled wrapper declared at the module top (`Root`, or `Styled<X>` for leaves), keyed off a prop like mode or drag state. The class-merge helper combines conditional/state classes with an incoming `className` only, never static class lists. One utility library, one consistent alias, for the common helpers (find, defaults, isEmpty, unique-id). Entrance animation is one small repeated preset, slide up while fading in, applied only to list/header wrappers, never leaf detail components. Conditional styling uses the array form of the style prop. Custom styled-component props are lowercased to survive DOM forwarding rather than filtered. Tab panels toggle visibility with a hidden class, never unmount. Import order: third-party, then aliased internal/framework, then relative app imports.

**Conventions**

Formatting is delegated entirely to the project formatter, blank-line padding required around functions and `if` statements, unused imports error, unused vars warn with a `^_` ignore pattern, `console.log` disallowed (error channel only), each file exports components only to keep fast refresh working, hook lint rules stay on with explicit disable comments for intentional exceptions, no `import React` (new JSX runtime), prop-types off since TypeScript covers it, `type` preferred over `interface` (interface reserved for ambient/module-augmentation), imports use configured path aliases over long relative chains, framework/shared-layer code carries a consistent prefix, `.tsx` only when it contains JSX else `.ts`. Config registries are data-only objects/arrays in a dedicated configs directory, typed by importing the type from the consuming component rather than a local copy. Translation bundles register at module load under a feature namespace, each language bundle a single flat object with UPPER_SNAKE_CASE keys, read through a translation hook scoped to that namespace.

**Utilities & misc**

Shared dialogs go through a central registry keyed by id, opening spreads props with `open: true`, closing deletes the key, content supplied as a render-prop receiving the close handler and data; self-contained forms still get local state with a plain dialog, that split is by design. Notifications route through one utility with success/error variants. A debounce hook wraps the utility debounce in a stable, cancel-on-unmount callback for hover-intent and form auto-save; a deep-compare effect paired with debounce is the form-sync effect of choice. One pub/sub utility is the only event bus, one-time listeners remove themselves. One shared immutable nested-setter helper is reused app-wide. Drag-and-drop follows the context/droppable/draggable render-prop structure with early-bail guards in drag-end and generic reorder helpers. Date utilities import per-function, not as a namespace, relative labels use a distance formatter with a suffix, and a date picker inside the form controller bridges ISO strings and `Date` objects. `as const` stays reserved for query keys, `satisfies` is rarely used, status/variant types are union string literals not enums, module augmentation stays minimal, non-null `!` assertions are essentially never used in favor of optional chaining with `?? ''`/`|| ''` fallbacks. `useReducer` with a discriminated-union action type and `default: throw` is reserved for tightly coupled state. A nav item's `type` is one of a small fixed set of strings, and a collapsible item may itself be navigable.

**Done**

Passing type checks and lint is not done. Run the app, open every route the change touches in a browser, exercise each interaction it adds (create, edit, delete, search, going back), and read the console; a route that renders the wrong view or logs an error is a failed task. Say plainly what could not be checked.
